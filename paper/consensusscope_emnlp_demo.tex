\begin{abstract}
AI writing-feedback systems can generate fluent revision advice, but fluency is
not the same as pedagogical safety: a suggestion may preserve meaning, change a
student's intended claim, introduce unsupported evidence, or overcorrect a
draft. We formulate \emph{feedback-level safety routing} for ESL writing
feedback: given an AI feedback item and its local context, decide whether the
item can be released to students or must be reviewed by a teacher. We present
ConsensusScope, an interactive demo built around a Feedback Safety Graph
Routing algorithm. The algorithm first extracts deploy-time signals from the
target span, surrounding context, AI suggestion, predicted issue type, evidence
status, and optional model agreement; then maps these signals to safety
dimensions such as local edit, meaning preservation, content grounding,
pedagogical tone, specificity, and model agreement; finally, it computes a
conservative risk route and materializes the decision as an auditable graph.
This design makes the algorithmic object of the demo a feedback item, not an
essay score or a final rewrite. The system normalizes feedback candidates into a
shared schema, constructs graphs without using gold labels or teacher ratings,
routes low-risk local edits separately from teacher-review items, and exports
graph-backed reports through a Streamlit/FastAPI implementation. We evaluate
the routing algorithm with a synthetic stress suite, a public learner-corpus
benchmark derived from JFLEG, CoNLL-2014, FCE, and W\&I+LOCNESS, and a
30-item two-teacher diagnostic pilot. Across 349,782 generated feedback
candidates, the default policy auto-routes 32.9\% of candidates while sending
all constructed incorrect or unsafe candidates to review; the teacher pilot
shows 0.857 auto-accept precision against teacher-safe items and 0.694
within-one-point teacher agreement. These results support the graph-backed
safety-routing claim, not classroom learning outcomes or real LLM feedback
quality.
\end{abstract}

\section{Introduction}

AI writing feedback is useful only when teachers can control what reaches a
student. Existing educational NLP work includes grammatical error correction
(GEC) shared tasks~\cite{ng-etal-2014-conll,bryant-etal-2019-bea},
learner-writing corpora such as FCE and JFLEG~\cite{yannakoudakis2011fce,
napoles-etal-2017-jfleg}, and writing-support systems that help students revise
drafts~\cite{madnani-etal-2018-writing}. Recent LLMs make feedback generation
easier, but they also increase the need for review: a fluent comment may be
locally grammatical while being pedagogically unsafe, unsupported, or too
interventionist.

ConsensusScope addresses this gap as an algorithmic routing problem rather than
an automatic essay-scoring problem. Given an ESL draft and a set of AI-style
feedback candidates, the target output is an item-level route:
\texttt{auto\_accept}, \texttt{teacher\_review}, or
\texttt{needs\_more\_evidence}. The technical challenge is that a feedback item
cannot be judged from its issue label alone. A grammar suggestion may be safe in
one context but wrong after a modal verb; a vocabulary edit may be fluent but
shift meaning; and a persuasive content suggestion may introduce evidence that
the student never provided.

The core idea is to convert each feedback item into a Feedback Safety Graph
before making it student-facing. Instead of reducing feedback to one confidence
score, the graph records how the target span, AI suggestion, predicted issue
type, evidence status, extracted safety signals, and final route support one
another. This graph representation lets the system expose the reason for a
route, not merely the route itself.

This framing is intentionally practical. It supports teachers who need to
triage AI feedback before student release, educational NLP developers who need
observable failure modes, and researchers studying reliability in
human-in-the-loop feedback pipelines.

The demo contributes: (1) a feedback-level safety-routing formulation for
AI-generated ESL writing feedback; (2) a Feedback Safety Graph Routing algorithm
that extracts deploy-time safety signals, maps them to explicit graph
dimensions, and applies conservative route thresholds without using teacher
labels at inference time; (3) a usable Streamlit/FastAPI system for single-essay
review, batch review, teacher queueing, evaluation, and graph-backed report
export; and (4) a reproducible evaluation package that combines public
learner-corpus routing diagnostics with a two-teacher offline pilot.

\section{Related Work}

\paragraph{Learner writing and GEC.}
GEC benchmarks have provided standardized correction tasks and learner-writing
data, including CoNLL-2014~\cite{ng-etal-2014-conll}, BEA-2019
W\&I+LOCNESS~\cite{bryant-etal-2019-bea}, FCE~\cite{yannakoudakis2011fce}, and
JFLEG~\cite{napoles-etal-2017-jfleg}. These datasets primarily evaluate
correction quality. ConsensusScope instead uses their correction annotations as
offline evidence for a downstream question: whether a feedback-routing policy
keeps risky or incorrect suggestions in a review queue.

\paragraph{Automated writing feedback.}
Automated writing systems can provide revision support, but classroom use
depends on how learners and teachers interpret the feedback
~\cite{madnani-etal-2018-writing,ranalli2018automated}. ConsensusScope follows
this caution by avoiding a teacher-replacement claim. It is designed to make AI
feedback inspectable and triageable before it becomes student-facing.

\paragraph{LLM reliability and adjudication.}
Multi-output and judge-based methods can help select answers or evaluate
generations~\cite{wang2023selfconsistency,zheng2023judging,liu2023geval}.
However, consensus or judge confidence is not equivalent to educational safety.
Our demo treats model agreement as one observable signal, alongside issue type,
evidence status, meaning-change warnings, unsupported-claim cues, tone-safety
cues, and parse errors.

\section{Comparison with Existing Systems}

ConsensusScope differs from existing writing-support and evaluation systems in
the unit of decision it makes visible. GEC and automated writing-feedback tools
focus on producing or scoring revisions; essay-scoring systems assign
essay-level quality signals; and LLM-as-judge workflows assess generations
after they are produced. ConsensusScope instead routes each \emph{feedback
item} before it reaches a student, exposing the graph evidence behind release
or review decisions (Table~\ref{tab:comparison}).

\section{Feedback Safety Graph Routing}

ConsensusScope is organized around an item-level routing algorithm embedded in
a teacher-facing review system (Figure~\ref{fig:workflow}). A teacher can paste
a single anonymized ESL draft or upload a batch CSV. The system generates
no-API AI-style feedback candidates or accepts live provider outputs in the same
schema. Each feedback item is then screened by the Feedback Safety Graph Router
and displayed as either a low-risk local edit or a teacher-review item.

\paragraph{Unified feedback schema.}
Every feedback candidate is represented with a stable item-level schema:
\texttt{feedback\_item\_id}, \texttt{essay\_id}, \texttt{target\_span},
\texttt{surrounding\_context}, \texttt{ai\_suggestion},
\texttt{ai\_rationale}, \texttt{model\_source},
\texttt{issue\_type\_predicted}, and optional \texttt{model\_agreement}. This
schema lets deterministic demo reviewers and live OpenAI-compatible providers
feed the same routing and reporting components.

\paragraph{Problem definition.}
Let $f=(x,c,u,t,e,a)$ denote a feedback item with target span $x$, local
context $c$, AI suggestion $u$, predicted issue type $t$, evidence status $e$,
and optional agreement signal $a$. The router estimates
$R(f)=(r,s,G)$, where $r$ is a release route, $s \in [0,1]$ is a bounded risk
score, and $G$ is an auditable graph connecting the observable signals to the
route. The deploy-time objective is conservative: release only items whose
observable signals indicate low-risk local feedback, while sending ambiguous,
unsupported, meaning-changing, or unsafe items to teacher review.

\paragraph{Algorithm.}
The procedure in Figure~\ref{fig:routing-procedure} summarizes the Feedback
Safety Graph Router. The algorithm first extracts deploy-time signals from the
feedback item. These
signals include issue-type risk, parse failure, evidence support or conflict,
model agreement, meaning-change cues, semantic drift pairs such as
\textit{remember} $\rightarrow$ \textit{learned}, wrong modal-verb corrections
such as \textit{can make} $\rightarrow$ \textit{makes}, unsupported external
claims, whole-draft rewriting, harsh tone, teacher-dependent wording, and broad
target spans. Each signal contributes to a bounded risk score
$s \in [0,1]$ and to a set of human-readable risk reasons. The reasons are then
projected into six graph dimensions: local edit, meaning preservation, content
grounding, pedagogical tone, feedback specificity, and model agreement.

\begin{figure}[t]
\centering
\fbox{
\begin{minipage}{0.92\linewidth}
\small
\textbf{Feedback Safety Graph Routing Procedure}\\
\textbf{Input:} feedback item $f$, local context $c$, evidence status $e$, optional model agreement $a$\\
\textbf{Output:} route $r$, risk level $\ell$, risk score $s$, graph $G$\\
1. Extract deploy-time signals from $(f,c,e,a)$\\
2. Map signals to risk reasons and safety dimensions\\
3. Compute bounded risk score $s$ from additive safety evidence\\
4. If parsing fails, set $r=\texttt{needs\_more\_evidence}$\\
5. Else if $s \geq 0.72$, set $\ell=\texttt{high}$ and $r=\texttt{teacher\_review}$\\
6. Else if $s \geq 0.32$, set $\ell=\texttt{medium}$ and $r=\texttt{teacher\_review}$\\
7. Else set $\ell=\texttt{low}$ and $r=\texttt{auto\_accept}$\\
8. Build graph $G$ with target span, suggestion, evidence, active dimensions, and route
\end{minipage}}
\caption{The routing algorithm uses deploy-time signals only. Teacher ratings
and public-corpus gold corrections are reserved for offline evaluation.}
\label{fig:routing-procedure}
\end{figure}

\paragraph{Graph construction.}
For each feedback item, ConsensusScope constructs a compact directed graph with
the core path \texttt{target span -> AI suggestion -> active safety dimension ->
routing decision}. Graph nodes represent the student target span, surrounding
context, AI suggestion, optional rationale, predicted issue type, evidence
signal, activated safety dimensions, and route. Edges capture relations such as
\texttt{contains}, \texttt{is\_revised\_by}, \texttt{activates}, and
\texttt{justifies\_route}. The exported route includes graph dimensions, active
signals, a path summary, and JSON node/edge records.

\paragraph{Routing outputs.}
For each feedback item, the system outputs \texttt{risk\_level},
\texttt{recommended\_action}, \texttt{risk\_reasons},
\texttt{meaning\_preservation\_predicted}, \texttt{risk\_score},
\texttt{review\_confidence}, \texttt{evidence\_signal},
\texttt{review\_priority}, graph fields such as
\texttt{safety\_graph\_path} and \texttt{safety\_graph\_summary}, and a short
explanation. Low-risk grammar,
spelling, punctuation, and vocabulary edits can be routed to
\texttt{auto\_accept}; medium- and high-risk items are routed to teacher
review, more-evidence, or reject states.

\section{Target Users and Use Cases}

The primary users are writing teachers, educational NLP developers, and NLP
researchers. Teachers can inspect which AI suggestions require judgment before
student release. Developers can use the normalized schema and saved routing
records to debug feedback pipelines. Researchers can test review-routing
policies, compare risk signals, and analyze cases where generated feedback may
be grammatically fluent but educationally unsafe. The system is especially
suited for settings that need human-review routing rather than fully automatic
writing evaluation.

\section{Evaluation}

We evaluate the implemented routing algorithm, not a full writing-feedback
generation model. The evaluation asks whether Feedback Safety Graph Routing
separates safe local edits from feedback that is incorrect, meaning-changing,
unsupported, or unsafe, and whether the graph signals exposed by the algorithm
match teacher-facing diagnostic patterns. We use three types of evidence.

\paragraph{Algorithmic stress checks.}
The packaged demo contains 15 feedback items with expected routes and 16
stress-test cases for dangerous suggestions such as thesis reversal,
whole-essay rewriting, unsupported factual claims, harsh tone, low agreement,
and parse failures. The current router matches the expected action and risk
labels on all 31 items. This is an algorithm sanity check rather than a
classroom outcome study.

\paragraph{Public learner-corpus benchmark.}
We construct an offline routing benchmark from public learner-correction
corpora. For each original/corrected sentence pair, we align source and
reference tokens to create feedback-level gold edits. We then generate one
gold-derived correct feedback candidate and one or more deliberately risky
distractor candidates for each edit. The router sees only the deploy-time
feedback fields; gold labels are used afterward to compute whether incorrect
or unsafe candidates were routed to review. Table~\ref{tab:public} reports the
runs completed on directly downloadable public data.

\paragraph{Two-teacher diagnostic pilot.}
To test whether the review routes align with human judgments, we collected a
small blind pilot from two English teachers over 30 anonymized AI feedback
items. Each teacher rated correctness, meaning preservation, student
readiness, usefulness, clarity, and direct-release suitability on 1--5 scales.
The teacher ratings are used only as offline diagnostics. They are not visible
to the deploy-time router. The pilot identified three borderline
auto-release patterns that are observable at deploy time: teacher-dependent
wording (``if the teacher wants''), semantic drift in vocabulary edits
(``remember'' to ``learned''), and wrong local grammar corrections after modal
verbs (``can make'' to ``makes''). We added conservative graph signals for
these cases without using teacher labels during routing. On the 30-item pilot,
the final router sends 76.7\% of items to review, reaches 1.000 recall for
teacher-marked review-needed items and teacher-marked unsafe items, and obtains
0.857 auto-accept precision against teacher-safe items
(Table~\ref{tab:teacherpilot}). The mean within-one-point agreement between
the two teachers over six rating dimensions is 0.694.

\paragraph{Review-routing utility.}
Table~\ref{tab:policy} summarizes the pooled policy results over 349,782
feedback candidates. The default policy accepts only low-risk items and routes
medium/high-risk items to review. It auto-routes 32.9\% of candidates while
preserving all constructed incorrect or unsafe candidates in the review queue.
The 1.000 auto accuracy should be interpreted narrowly: correct candidates are
derived from public gold corrections, and incorrect candidates are constructed
risk distractors. The number validates routing behavior under controlled
conditions; it is not a claim that real LLM feedback is always correct.

\section{Demo Scenario}

The two-and-a-half-minute demo follows a teacher workflow. The presenter opens
Review Workspace, runs Single Essay Review on a packaged anonymized ESL draft,
shows routed feedback items, and inspects Feedback Safety Graph paths for
auto-accepted local edits and teacher-review items. The demo then processes a
batch CSV, opens AI Feedback Comparison, selects a high-risk item in Teacher
Queue, and exports a Markdown report. The Effectiveness Evaluation page shows
the synthetic stress-test metrics and the public learner-corpus aggregate
table.

\section{Release and Reproducibility}

ConsensusScope is released under the MIT License. The public repository and
live demo are available at:
\url{https://github.com/yyting2006-ai/ConsensusScope} and
\url{https://demo.consensusscope.cn/}. The backend API documentation is
available at \url{https://api.consensusscope.cn/docs}. The hosted demo is
served through a Cloudflare named tunnel to a self-hosted Streamlit and FastAPI
deployment rather than Streamlit Community Cloud, which avoids cold-start
failures during review. The demo can be installed and run with:

\begin{verbatim}
pip install -r requirements.txt
streamlit run app/streamlit_app.py \
  --server.port 8502
\end{verbatim}

The backend API can be started separately with:
\begin{verbatim}
uvicorn backend.app:app --host 127.0.0.1 \
  --port 7864
\end{verbatim}

The public benchmark can be reproduced with
\texttt{scripts/run\_public\_gec\_benchmark.py}. JFLEG can be downloaded
automatically by the script. CoNLL-2014 annotated test data and BEA-2019 FCE
and W\&I+LOCNESS data are downloaded from their official release pages. Raw
corpora and per-item derived outputs are not committed to the repository;
aggregate result tables are included for inspection.

\section{Ethics and Limitations}

ConsensusScope is a teacher-support tool, not an automatic essay scorer or
teacher replacement. Users should upload only anonymized student writing; names,
student IDs, emails, class identifiers, and other personally identifiable
information should be removed before use. The current benchmark validates
graph-backed review-routing behavior with public correction labels and
constructed distractors. It does not measure student learning, teacher
satisfaction, time-on-task, or real LLM feedback quality. The two-teacher
pilot is preliminary and covers 30 feedback items; it should be read as a
diagnostic check for routing behavior, not as a classroom user study. Future
work should expand the teacher sample, add authentic anonymized classroom
data, and keep deploy-time graph signals separate from offline diagnostic
ratings.

\section{Conclusion}

ConsensusScope demonstrates Feedback Safety Graph Routing for AI-generated ESL
writing feedback. By defining feedback-level safety routing, extracting
deploy-time risk signals, constructing item-level safety graphs, and routing
uncertain or unsafe suggestions into a teacher queue, the system turns AI
feedback from a final rewrite into an auditable teacher-in-the-loop decision.
